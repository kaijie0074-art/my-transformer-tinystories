# 任务 A：模型原理与错误复盘

## 范围与证据

我在这个项目中从随机初始化训练英文 TinyStories 自回归语言模型；模型结构和训练流程由项目代码实现，但分词使用成熟的 `tokenizers` 库，张量计算、自动求导和 AdamW 使用 Apple MLX。我在代码编写、实验设计、运行和分析中使用了 AI 协助，并不是独立从零实现所有底层算法。

本文区分两类材料：模型和本次数据处理以项目代码、现有记录为依据；下文四段早期经历是**我的事后回顾**，本仓库没有对应的原始日志，不能当作本次 A/B 训练的复现结果或根因证明。[现有对照报告](学习率预热-技术报告-20261114.md)记录的是另一次学习率路径对照。

## 一、模型如何学习预测下一个 token

以下尺寸对应本次正式实验，而非所有可配置运行的固定值：词表 10,000、上下文 512、8 层、8 个注意力头、模型宽度 512、MLP 隐藏维度 3,072；每个微批次 5 条序列，累积 8 次梯度。实现见 [model.py](../model.py) 和 [train.py](../train.py)，实验设置见[技术报告](学习率预热-技术报告-20261114.md)。

1. **文本到 token。** 本地训练的 Byte-level BPE tokenizer 将故事转换为整数 ID，数据按 `[BOS] + 正文 + [EOS]` 存储。训练时从 token 流采样长度 513 的连续片段，前 512 个作为输入 `x`，后 512 个作为目标 `y`：目标相对输入右移一个位置。`x` 和 `y` 均为 `[5, 512]`；token 不等同于字符或单词。
2. **词嵌入与位置嵌入。** 每个 token ID 查表得到 512 维向量，位置 0～511 也查表得到 512 维向量；两者相加，得到 `[5, 512, 512]`。位置嵌入让模型区分顺序。
3. **因果多头注意力。** 每个 Transformer 块先做 RMSNorm，再把输入线性投影为 Q、K、V；各自从 `[5, 512, 512]` 拆成 `[5, 8, 512, 64]`。缩放点积注意力按每头维度的平方根缩放，并使用因果掩码，使每个位置只能关注自身及之前的位置，不能看到未来目标。各头合并并投影回 512 维，再与该子层输入相加形成残差。
4. **前馈网络与残差。** 注意力残差结果先经过另一层 RMSNorm，再经 `512 → 3072 → GELU → 512` 的逐位置 MLP，并与其输入相加。以上块重复 8 次，最后再做 RMSNorm。
5. **输出与损失。** 独立于输入词嵌入的输出投影将每个位置映射到 10,000 个词表 logits，形状为 `[5, 512, 10000]`。训练将 logits 与右移目标计算平均 next-token cross entropy：正确的下一个 token 被赋予的概率越低，损失通常越大。生成时则根据已有上下文选择下一个 token，再将其接回上下文；推理可只投影最后位置。
6. **求梯度和更新。** `nn.value_and_grad` 对模型及损失自动求梯度。每个优化步顺序处理 8 个微批次，把梯度相加后除以 8，再由 MLX AdamW 按当前学习率更新一次；每次更新涉及 `5 × 8 × 512 = 20,480` 个目标 token 位置，采样位置可以重复。逐个求值微批次有助于避免同时保留多个计算图。实验使用峰值学习率 0.0006、weight decay 0.1；A 组前 500 步线性预热，之后余弦下降。训练脚本的默认梯度累积值是 1，8 是本次实验配置。

## 二、四次早期经历：现象、边界与下一次检查

### 1. 中文数据、乱码与效果没有提升

**我的回顾：** 我早期选用中文数据，曾遇到生成乱码，也多次看到训练效果没有提升；我怀疑过中文的多字节编码。

**证据边界：** 中文 UTF-8 字符往往占多个字节，但多字节本身不必然导致乱码；本仓库没有那次的原始输入、tokenizer、输出或日志，不能确定实际原因，也不能把乱码和效果不提升都归因于编码。

**我会怎样检查：** 从原始文件的字节入手，确认写入和读取都明确使用 UTF-8，并比较解码后的原文；对含中文、标点、换行及特殊符号的样本，用同一个 tokenizer 做 encode→decode 往返，核对原文和还原结果，并检查未知 token、特殊 token、训练和推理使用的 tokenizer 是否一致。如果往返正确但生成仍差，再分别检查数据质量、训练 loss 和独立验证表现，而不是先认定编码有问题。

### 2. 照搬模型参数，机器中断和变慢

**我的回顾：** 我没有先检查电脑配置，也没有做短试跑，就照搬模型参数；系统多次中断并明显变慢。我的分析是内存不足导致了训练中断。

**证据边界：** 没有当时的内存监控、系统错误或堆栈记录，不能断言是具体的 OOM，也不能排除其他资源或系统原因。

**我会怎样检查：** 先确认可用内存、磁盘、电源及训练目标，再估算模型参数、优化器状态、激活和批量的资源开销；从小模型、短上下文和少量步数试跑，记录系统内存压力、MLX 内存指标、吞吐和中断信息，再逐项调整。梯度累积可以降低单次微批次的内存需求，但不能消除模型和优化器状态的占用。

### 3. 用训练文本评估，结果过于乐观

**我的回顾：** 我以前没有留独立验证集，用训练文本评估时感觉效果较好，但实际生成体验一般。训练数据上的好表现不等于对未见内容的泛化，也不保证生成质量。

**当前项目的区别：** 本次 TinyStories 使用独立验证划分，并从验证集中排除与训练故事原文完全一致的 6,601 篇；近似重复没有检查，所以不能声称完全无数据泄漏。[数据准备说明](../README.md#数据准备)和[去重实现](../clean_validation.py)可供复核。正式实验的验证 loss 是固定抽样，而非完整验证集评估；生成体验还需单独检查。这个精确去重案例是本次项目记录，不是我早期经历的日志。

### 4. FP16 的 NaN 与优化器精度

**我的回顾：** 我曾在 FP16 训练中遇到 loss 为 NaN；AI 当时将原因归为学习率，但修改学习率后仍出现 NaN。后来我发现当时 FP16 更新没有显式转换为 FP32，AdamW 的分母出现了零，我将其作为 NaN 的原因。

**证据边界与可能机制：** 上述是我对那次过程的回顾；本项目没有保留当时的参数、梯度和优化器状态 dtype、epsilon 或错误堆栈，所以目前无法从现有日志独立核实分母变为零的具体环节，也不能把它冒充为本项目已复现并修复的故障。AdamW 更新通常包含类似 `sqrt(v̂) + ε` 的分母：若相关计算或存储确实使用 FP16，极小的二阶矩或 epsilon 可能因精度和下溢变成零，进而产生非有限更新；具体是否发生取决于实现、数值与计算 dtype。NaN 也可能来自其他环节，不能把我的一次经历推广为所有 FP16 都会失败。

**我会怎样验证：** 保存最小可复现配置，记录首个非有限值出现的步骤、loss、梯度、参数、AdamW 一阶/二阶状态、实际计算与存储 dtype、epsilon 和更新前后的数值；在其他条件固定时比较 FP16 与更新及优化器状态使用 FP32 的运行，并检查分母是否真的为零、非有限值是否首先出现在更新环节。只有这些证据才能支持或否定该机制；若仍失败，再追查前向、梯度、数据和学习率等其他来源。

## 三、我的核心收获

我应该先明确目标，再一起考虑目标数据、tokenizer、硬件、数值精度和验证方式，先做能检查数据往返、内存与 loss 的短试跑，再投入长训练。AI 的诊断可以提供假设，但我要用可复核的日志和对照验证；把历史回忆、当前观察和已证实的因果结论分开，才能减少可避免的试错。
